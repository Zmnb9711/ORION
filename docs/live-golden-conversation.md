# Live Golden Conversation — Mode A field vertical

Status: **IMPLEMENTATION READY FOR FIELD**. This status is not a field PASS.
`LIVE GOLDEN PASS` requires a real spoken run and an explicit human acoustic
review through the official SRS Client.

## Bounded architecture

The first field vertical deliberately uses **Mode A — controlled acoustic
Golden proof**. DCS is not required and no live runway awareness is claimed.
Each operational case gets a fresh, bounded `CONTROLLED GOLDEN ATC FIXTURE`
with callsign `Viper 2-1`, runway `07/25`, Tower authority and a clear/fresh
runway. The existing deterministic Tower implementation still owns the takeoff
decision.

The implemented path is:

```text
official SRS Client microphone/PTT
→ official SRS Server
→ existing ORION production SRS RX
→ existing Yandex Realtime session and final user transcript
→ one Qwen3.6 strict FREE/OPERATIONAL decomposition
→ existing Golden Takeoff ATC decision
→ FAP_RUSSIAN_ATC experimental Pilot Phraseology entry
→ Core-owned deterministic composition
→ existing SpeechKit REST v1 client
→ finalized PCM
→ existing RadioRouter
→ existing SrsRadioTransportAdapter
→ existing field-proven SRS TX worker
→ official SRS Client
→ human acoustic review
```

There is no second microphone owner, second Yandex Realtime session, second SRS
TX worker, new packetizer or Qwen-Realtime-to-SRS transport. The final composed
text is never sent back to Qwen. Qwen only returns the strict decomposition and
the untrusted FREE response. Core owns the operational decision, phraseology
and final ordering.

While Live Golden is active, ORION sends the documented Yandex Realtime
`response.cancel` event for the provider's normal response and independently
drops any raced provider output PCM at the existing SRS endpoint. Thus normal
Yandex response audio cannot compete with the protected SpeechKit response.
The transcript callback is bounded and hands the finalized input to one
background case worker; it never blocks the Realtime receive loop.

## Field corpus and expected response structure

The Launcher presents these cases in order without configuration edits:

1. `Добрый день! Разрешите взлёт.`
2. `Здравствуйте! Можно взлетать?`
3. `Доброе утро, башня. Готов к взлёту.`
4. `Башня, приветствую. Запрашиваю разрешение на взлёт.`
5. `Добрый вечер! Мы готовы, разрешите взлёт.`
6. `Башня, рад вас слышать. Прошу разрешить взлёт.`
7. Control: `Разрешите взлёт.`
8. Control: `Добрый день! Как дела?`

For the six mixed cases the complete response is not hardcoded. Its first FREE
sentence is generated by Qwen from only the conversational part and may vary.
It must be followed exactly once by the protected experimental phrase:

```text
Viper 2-1, полоса 07/25, взлёт разрешён.
```

The pure operational control contains no FREE greeting. The pure conversational
control contains a FREE reply and no takeoff fragment, ATC decision or
phraseology entry.

## Evidence and safety gates

The existing Test Evidence ZIP gains `live-golden-summary.json` and, when the
explicit checkbox is selected, one WAV per completed response under
`live-golden-audio/`. These WAVs are the finalized SpeechKit PCM **entering
SRS**, not receiver-side recordings.

Each case records the strongest directly observable correlation for real input,
the final transcript, Qwen response ID/attempt count, strict decomposition,
deterministic ATC result, profile, phraseology entry, protected slots, FREE and
protected fragments, final composed text/hash, SpeechKit correlation and PCM
metadata/hash, RadioRouter/SRS completion, stage latency and explicit acoustic
review. Credentials, Authorization, provider bodies, microphone PCM, SRS RX
audio and receiver-side audio are excluded.

The evidence session records the packaged Git SHA, branch and ORION version.
Frozen Core resolves these values from a bounded `build-identity.json` marker
placed beside the delivered executable. Source runs resolve the current Git ref
without invoking Git.

The case lifecycle is serialized:

```text
WAITING_INPUT → PROCESSING → AWAITING_REVIEW → next case
```

Duplicate provider item IDs, extra utterances during processing/review and stale
work after operator stop cannot create a second transmission. Invalid Qwen
output, semantic mismatch, unavailable ATC, phraseology failure, SpeechKit
failure or SRS unreadiness fails closed and never falls back to generative radio
speech.

## Controlled no-DCS field procedure

1. Install or run the fresh Live Golden product build. Do not start DCS.
2. Start the official SRS Server with EAM enabled for blue coalition.
3. Start the official SRS Client, join blue, set Radio 1 to `251.000 MHz AM`,
   select the intended microphone/headphones and verify Common PTT.
4. Start ORION Launcher. Select `Yandex Realtime` and `SRS Radio`, use the same
   SRS host/port/EAM password and `251.000 MHz AM`, then press `START LIVE`.
5. Wait until Launcher reports the Yandex+SRS session running and the radio is
   fully registered.
6. Press `START TEST SESSION`. Leave `Include finalized SpeechKit→SRS WAVs in
   Test Evidence` enabled.
7. Press `START LIVE GOLDEN`. Read only the phrase shown after `SAY:`. Hold
   Common PTT, speak naturally, release PTT, and wait for ORION's complete radio
   response.
8. Listen through the official SRS Client. Select exactly `CLEAR`, `UNCLEAR`, or
   `NOT_HEARD`, then press `RECORD CASE REVIEW`. The next phrase appears only
   after the review is stored.
9. Repeat through all six primary cases and the two controls. Do not type an
   expected response and do not change configuration between cases.
10. Confirm Launcher reports all 8 cases complete, then press `STOP & EXPORT
    TEST SESSION`. Use `OPEN EXPORT FOLDER` to retrieve the ZIP.

If any case fails, do not repeat phrases into an unresolved state. Press `STOP
LIVE GOLDEN`, export the current evidence, and classify that run as
`LIVE GOLDEN FAIL`.

## Field classification

`LIVE GOLDEN PASS` requires all six primary cases to prove the complete internal
chain and receive a human `clear` acoustic review. Controls should also behave
as specified. A local `tx_completed` or non-empty WAV alone proves only that
ORION transmitted finalized audio; it never proves reception in the user's
headphones.
