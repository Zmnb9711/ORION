# ORION Virtual ATC Interface Contract

Status: mandatory architecture contract for Virtual ATC Core (#61)

## Principle

ORION is the primary pilot-facing ATC interface for both carrier and land-based operations.

The normal user interaction path is:

`PILOT <-> ORION <-> DCS`

not:

`PILOT <-> DCS ATC MENU`

For supported procedures, the pilot should not need to navigate the standard DCS ATC/radio menu manually. The pilot communicates naturally by voice with the appropriate ORION controller role, and ORION maintains the ATC session, controller ownership, procedural state, acknowledgement state and traffic context.

## Scope

This principle applies equally to:

- carrier Air Boss/PriFly
- carrier Departure
- carrier Marshal
- carrier Approach
- carrier Tower
- carrier LSO
- airport Ground
- airport Tower
- airport Departure
- airport Approach
- future sector/center-style controllers when implemented

Carrier-specific and fixed-airfield procedures remain separate domain engines, but they share the same pilot-interface contract.

## DCS as simulator backend

DCS remains the simulator authority for simulator-native state and events. ORION does not attempt to replace the simulator itself.

Where DCS requires a native ATC interaction or state transition for mission logic, Supercarrier behavior, AI traffic behavior or internal scripting, the appropriate DCS adapter should synchronize that state automatically when technically possible.

Examples may include native inbound/contact/approach/landing/takeoff/departure events, radio-menu commands, mission-script callbacks or equivalent simulator hooks.

The pilot should not be required to duplicate an instruction manually in the DCS menu when ORION can safely perform or mirror that synchronization.

## Adapter boundary

The generic ATC core must not contain DCS menu logic.

Domain adapters own simulator-specific synchronization:

- `AirportDcsAdapter`
- `CarrierDcsAdapter`

Adapters translate between ORION semantic ATC actions and available DCS-native events/calls. They also expose capability and freshness metadata.

A semantic action such as `request_startup`, `request_taxi`, `inbound`, `ready_for_departure`, `commence`, `visual_acquired`, `ball_call`, or `request_landing` is generated by an ATC procedure engine. The adapter decides whether a native DCS synchronization action exists and is supported.

## Capability modes

Each DCS-backed semantic action must report one of the generic capability states:

- `SUPPORTED` — ORION can synchronize the corresponding native DCS state/action.
- `UNSUPPORTED` — no supported automatic DCS synchronization is available.
- `UNKNOWN` — support cannot currently be established reliably.

Unknown support is not treated as supported.

## Operating modes

Virtual ATC should support three explicit integration modes.

### ORION_PRIMARY

Default target mode.

The pilot talks only to ORION for normal ATC workflow. ORION automatically mirrors/synchronizes DCS-native ATC interactions where required and supported.

### ORION_WITH_NATIVE_FALLBACK

ORION remains the primary controller, but if a required native DCS transition cannot be automated, ORION can explicitly tell the pilot that a native DCS action is required.

This is a degraded compatibility mode, not the desired end-state UX.

### NATIVE_FALLBACK

Used when ORION loses the capability, telemetry or state confidence required to continue safely. The session is marked degraded and the pilot can return to standard DCS ATC procedures.

ORION must never falsely claim that native DCS synchronization occurred when it did not.

## Fixed-airfield workflow target

A normal airfield workflow should ultimately be possible entirely by voice, for example:

`startup/request clearance -> Ground -> taxi -> hold short -> Tower -> takeoff -> Departure`

and on arrival:

`Approach -> Tower -> landing -> Ground -> parking`

The exact procedure and phraseology depend on airport, mission configuration and future ATC procedure engines, but manual traversal of the standard DCS radio menu should not be part of the intended normal workflow.

## Carrier workflow target

Carrier workflows use the same interface principle:

`Departure` for outbound airborne control and

`Marshal -> Approach -> Tower/PriFly -> LSO` for recovery, with Air Boss/Deck roles as applicable.

DCS Supercarrier native state may still be synchronized underneath through `CarrierDcsAdapter`.

## Authority and acknowledgement

Simulator synchronization does not itself grant ATC authority. Controller authority remains governed by `ControllerAuthorityScope` and `ControllerHandoffTransaction`.

Likewise, a successful native DCS menu/API action is not automatically equivalent to pilot acknowledgement unless the procedure explicitly defines the simulator event as acceptable acknowledgement evidence.

The ATC engine must preserve the distinction between:

- ORION instruction transmitted
- pilot acknowledgement
- observed aircraft compliance
- native DCS synchronization success

## Failure semantics

If DCS synchronization fails:

1. keep the ORION ATC session and procedural state intact;
2. record a machine-readable integration failure event;
3. apply a degraded integration overlay/capability state;
4. do not silently repeat unsafe commands indefinitely;
5. use bounded retry if the action is retryable;
6. request a native fallback action from the pilot only when necessary;
7. retain a clear path back to standard DCS ATC.

A failed adapter call must not fabricate simulator state.

## Voice-first UX invariant

ORION controller voices are the pilot-facing experience. Native DCS menu synchronization should normally be silent and invisible.

The pilot should hear role-correct controllers and handoffs rather than system messages about implementation details, except when degraded/fallback operation materially affects what the pilot must do.

## Common-core implications for #61

Virtual ATC Core must remain compatible with this contract by supporting:

- semantic `OperationalInstruction` actions independent of DCS implementation details;
- authority-scoped controller ownership;
- explicit acknowledgements and observed-compliance evidence;
- capability/freshness metadata;
- integration/degraded operational overlays;
- reasoned event history for native synchronization attempts/results;
- session continuity across ORION-primary and fallback modes;
- clean adapter interfaces without runway- or carrier-specific assumptions.

## Design decision

The ORION-first interface is mandatory for both Carrier ATC and fixed-airfield ATC. Standard DCS ATC/radio-menu procedures are retained as simulator backend and safety/compatibility fallback, not as the intended normal pilot-facing workflow.
